# 开发文档 - 智能环卫机器人控制系统

> 整合来源：`项目文档` 目录下所有需求文档。  
> 整合原则：以 V3.0 实际平台为主线，V2.5 与模块细化文档作为补充；当前开发不再采用 2D LiDAR SLAM、ONNX Runtime 部署、Jetson 假设、通用 `motion_controller` 路线。

## 1. 项目总览

本项目面向智能环卫机器人实车落地，部署于移远 Quectel QSM602HA-GL 开发板，硬件核心为 D-Robotics X5 SoC、ARM64 Ubuntu 22.04、ROS2 Humble、4GB 内存。系统通过 CAN 总线直驱 OID FOC 无刷电机，实现从遥控底盘行驶，到毫米波雷达 + 视觉融合感知，再到自主覆盖清扫的分期演进。

### 1.1 当前权威路线

| 项目 | 当前落地选择 |
| --- | --- |
| 目标平台 | ARM64 QSM602HA-GL / D-Robotics X5 |
| 操作系统 | Ubuntu 22.04 + ROS2 Humble |
| 底盘控制 | CAN 500Kbps 直驱 OID FOC 电机 |
| 电机控制模式 | `0x01` 电流控制；驱动固件不响应 `0x02` 速度命令 |
| 一期控制输入 | SBUS 遥控器 |
| 一期定位 | 轮式里程计 + IMU yaw，RTK 发布 `/fix` |
| 二期避障 | 毫米波雷达 + 视觉后融合 |
| 二期视觉推理 | Horizon X5 BPU，`libdnn.so` + `.hbm` 模型 |
| 不采用 | 2D LiDAR 路线、LiDAR SLAM、ONNX Runtime 端侧推理、通用 `motion_controller` |

### 1.2 三期演进

| 期数 | 目标 | 交付边界 |
| --- | --- | --- |
| 一期：底盘打通 | 实车遥控行驶、安全停机、基础传感器链路 | `common`、`chassis_core`、`chassis_driver`、`remote_driver`、`imu_driver`、`rtk_driver`、`master_bridge` |
| 二期：感知清扫 | 自主路径、毫米波/视觉融合避障、清扫机构控制 | 扩展 `master_controller`、`path_planner`、`vision_detector`、`radar_driver`、`fusion_engine`、`cleaning_actuator` |
| 三期：产品化 | App/语音/远程监控、自动回充、区域任务、多机预留 | 不纳入近期实车闭环，需补齐电池、充电桩、远程协议等硬件与接口 |

## 2. 实施原则

1. V3.0 实际平台文档优先于 V2.5 通用架构文档。
2. `需求文档_参数与信号总表.md` 是参数、Topic、硬件读取路径的权威来源；参数冲突时以实际 YAML 运行值为准。
3. `需求文档_底盘核心架构.md` 是底盘控制实现细节来源；同事实车调试的 C++ WheelPID 逻辑应封装保留。
4. `需求文档_消息接口规范.md` 是自定义消息规范来源；短期仍保留 V3 已验证的 JSON Topic，如 `/chassis/intent`。
5. 实车安全优先于架构完整性：急停、失控保护、反馈超时、安全锁必须先于自主能力完成。
6. 二期模块只保留与 V3 路线兼容的内容：毫米波雷达、BPU 视觉、后融合、路径规划、清扫控制。
7. 不读取或依赖需求目录之外的代码现状；本文件只表达开发目标、接口、任务与验收。

## 3. 系统架构

### 3.1 一期底盘链路

```text
SBUS 遥控器
  -> remote_driver
  -> /joy
  -> master_bridge
  -> /chassis/intent JSON + /cmd_vel
  -> chassis_driver
  -> chassis_core.tick()
  -> CAN current frame
  -> OID FOC 电机 001-004

IMU /dev/qmi8658_imu -> imu_driver -> /imu/data -> chassis_driver
RTK /dev/ttyS2       -> rtk_driver -> /fix
chassis_driver       -> /odom + /tf + /chassis/status
```

一期核心验收是“可控、可停、可观测”：遥控链路稳定，CAN 电流控制有效，里程计/状态可读，急停和超时保护可靠。

### 3.2 二期感知清扫链路

```text
UnifiedCommand/AUTO_SWEEP
  -> master_controller(master_bridge 扩展)
  -> control/trigger_planning
  -> path_planner
  -> /chassis/intent 航点执行
  -> chassis_driver

vision_detector -> vision/detect/list -> fusion_engine
radar_driver    -> radar/obstacles     -> fusion_engine
fusion_engine   -> fusion/semantic_alert -> master_controller
fusion_engine   -> fusion/obstacle/decision -> path_planner

master_controller -> cleaning_actuator -> CAN ID 005 / 清扫机构
vision_detector -> vision/detect/cleanliness -> cleaning_actuator/master_controller
```

视觉数据不得直接驱动路径规划。所有会影响避障路径的视觉信息必须经过 `fusion_engine` 做空间关联后输出 `fusion/obstacle/decision`。

### 3.3 三期产品化链路

三期只作为架构预留：App、语音、远程监控、自动回充、区域任务管理、多机器人命名空间。当前文档不把它们作为近期交付项，除非补齐电池、充电桩、地图、通信协议与安全策略。

## 4. 硬件与参数

### 4.1 硬件接口

| 设备 | 路径/接口 | 用途 | 节点 |
| --- | --- | --- | --- |
| CAN 总线 | `can0`, 500Kbps | 4 个行走电机 + 刀盘电机 | `chassis_driver`, `cleaning_actuator` |
| SBUS 遥控 | `/dev/ttyS1` | MCU/port_bridge 转发 SBUS | `remote_driver` |
| SBUS 备用直连 | `/dev/ttyS7` | 标准 SBUS 8E2，备用 | 暂不作为主链路 |
| IMU | `/dev/qmi8658_imu` | QMI8658 6 轴原始数据 | `imu_driver` |
| RTK GNSS | `/dev/ttyS2` | NMEA 0183 / NTRIP | `rtk_driver` |
| BPU | `/dev/bpu`, `/dev/bpu_core0` | YOLO `.hbm` 推理 | `vision_detector` |
| 毫米波雷达 | `/rys_mmwave/*` PointCloud2 | 厂商驱动已发布的话题 | `radar_driver` |

### 4.2 CAN 协议

| 项 | 约定 |
| --- | --- |
| 帧类型 | 标准数据帧 11-bit ID |
| 多字节负载 | 大端 |
| 心跳 | `0x00`, DLC=1 |
| 电流控制 | `0x01`, `[cmd, int16 current]`, 单位 10mA |
| 速度控制 | `0x02`, 本机固件不响应，禁止作为控制方案 |
| 查询 | `0x0F`, byte1 查询码 |
| 转速查询码 | `0x01`, 响应 `DATA[2:6]` int32 big-endian ERPM |
| 电机 ID | `001` 左后, `002` 左前, `003` 右后, `004` 右前, `005` 刀盘 |

### 4.3 关键运行时参数

以下参数存在多文档数值差异，实施时必须以 `phase1_params.yaml` 的实际加载值为准。

| 参数组 | 关键项 | 开发要求 |
| --- | --- | --- |
| 电机硬件 | `pole_pairs=10`, `gear_ratio=5.2`, `motor_ids=[2,1,4,3]` | 统一 FL/RL/FR/RR 顺序 |
| 运动学 | `wheel_radius`, `track_width` | 只影响里程计，不影响 RPM 控制 |
| 控制模式 | `wheel_control_mode=current` | 强制电流模式 |
| 安全 | `failsafe_ms`, `speed_feedback_timeout_ms`, `wheel_overspeed_rpm` | 超时/超速必须锁止 |
| 航向 | `imu_heading_enable`, `heading_kp/ki/kd`, `imu_yaw_sign` | 直行纠偏依赖 IMU yaw |
| 遥控 | `throttle_channel`, `steering_channel`, `gear_channel`, `low_threshold`, `high_threshold` | 通道映射需实测确认 |
| ROS2 自主 | `ros2_enable`, `ros2_cmd_timeout_ms`, `max_accel_mps2` | 二期自主链路使用 |

## 5. 接口与数据流

### 5.1 一期 Topic

| Topic | 类型 | 发布者 | 订阅者 | 说明 |
| --- | --- | --- | --- | --- |
| `/joy` | `sensor_msgs/Joy` | `remote_driver` | `master_bridge` | 遥控归一化输入 |
| `/chassis/intent` | `std_msgs/String` JSON | `master_bridge` / 自主模块 | `chassis_driver` | 当前主控制接口 |
| `/cmd_vel` | `geometry_msgs/Twist` | `master_bridge` / 兼容源 | `chassis_driver` | 兼容接口 |
| `/imu/data` | `sensor_msgs/Imu` | `imu_driver` | `chassis_driver` | IMU yaw/角速度来源 |
| `/fix` | `sensor_msgs/NavSatFix` | `rtk_driver` | 外部/二期定位 | RTK GNSS |
| `/odom` | `nav_msgs/Odometry` | `chassis_driver` | `path_planner`, TF | 里程计 |
| `/tf` | `tf2_msgs/TFMessage` | `chassis_driver` | 全系统 | `odom -> base_link` |
| `/chassis/status` | `std_msgs/Float32MultiArray` | `chassis_driver` | 监控/调试 | 轮速、电流、yaw、estop |
| `/master/state` | `std_msgs/String` | `master_bridge` | 监控 | 状态机 |

### 5.2 `/chassis/intent` JSON

```json
{
  "throttle": -1.0,
  "steering": 0.0,
  "gear": "LOW",
  "mower": 0,
  "estop": 0
}
```

字段约束：

| 字段 | 含义 |
| --- | --- |
| `throttle` | 油门，范围 `-1.0..1.0` |
| `steering` | 转向，范围 `-1.0..1.0` |
| `gear` | `LOW` / `MID` / `HIGH` |
| `mower` | 刀盘/清扫机构开关，二期使用 |
| `estop` | 急停，`1` 表示立即停机 |

### 5.3 `/chassis/status` 布局

| 索引 | 字段 | 单位 |
| --- | --- | --- |
| 0 | FL RPM | RPM |
| 1 | RL RPM | RPM |
| 2 | FR RPM | RPM |
| 3 | RR RPM | RPM |
| 4 | yaw_deg | degree |
| 5 | yaw_rate_dps | degree/s |
| 6 | estop | 0/1 |
| 7 | FL current command | 10mA |
| 8 | RL current command | 10mA |
| 9 | FR current command | 10mA |
| 10 | RR current command | 10mA |
| 11-15 | reserved | - |

| Topic | 类型 | 发布者 | 订阅者 | 说明 |
| --- | --- | --- | --- | --- |

| `/vision/detect/list` | `DetectionArray` | `vision_detector` | `fusion_engine` | 视觉检测结果 |
| `/vision/detect/cleanliness` | `std_msgs/Float32` | `vision_detector` | `cleaning_actuator`, `master_controller` | 清洁度 |

### 5.5 自定义接口

`cleaning_robot_interfaces` 应至少包含：

| 类型 | 名称 | 用途 |
| --- | --- | --- |
| msg | `Detection`, `DetectionArray` | 视觉检测；`Detection.depth_m` 可为深度相机/融合提供真实距离 |
| msg | `TaskMode`, `TaskArea`, `CleanStrategy` | 主控向规划/清扫下发任务 |
| msg | `Path`, `PlannerState` | 路径输出和状态 |
| msg | `Fusion3DTarget`, `FusionDecision` | 后融合告警和避障决策 |
| msg | `Heartbeat`, `Alert`, `VisionStatus` | 运行状态与告警 |
| srv | `SetModel`, `GetStatus`, `SetPriority`, `SetMaxSpeed` | 配置与查询 |
| action | `NavigateToGoal`, `ExecuteCleanup` | 长任务 |

短期实现允许 JSON Topic 与自定义 msg 并存；中长期应将已稳定接口迁移为自定义消息，降低 JSON 字段漂移风险。

## 6. 模块开发说明

### 6.1 `cleaning_robot_common`

| 项 | 内容 |
| --- | --- |
| 目标 | 提供非 ROS 的共享 Python 库，统一配置、运动学、CAN 协议 |
| 职责 | `config.py`, `kinematics.py`, `can_protocol.py` |
| 输入/输出 | 无 ROS I/O，纯函数与常量 |
| 开发任务 | 汇总 CAN ID、SBUS 常量、IMU 校准、Topic 名；实现 `diff_decompose`, `erpm_to_ms`, `integrate_odom`, CAN 帧构造/解析 |
| 验收 | 单元测试覆盖运动学、CAN 字节序、ERPM 解析、四元数转换 |
| 风险 | 当前 `imu/remote/rtk` 文档中仍有独立常量，后续需收敛 |

### 6.2 `chassis_core`

| 项 | 内容 |
| --- | --- |
| 目标 | pybind11 封装 C++ 底盘控制核心，保留 WheelPID 实车调试逻辑 |
| 职责 | 纯计算，不做 ROS2、不做 CAN I/O |
| 输入 | `throttle`, `steering`, `gear`, `estop`, 每轮反馈 ERPM, IMU yaw/rate, 时间戳 |
| 输出 | 4 路 CAN 电流指令、安全锁状态、原因 |
| 开发任务 | 实现 `tick()`, `update_config()`, `reset_safety()`；支持 current 模式 PI、启动斜坡、原地旋转、航向保持、换向保持、档位 |
| 验收 | 无硬件单元测试 + 台架固定反馈测试；超速/反馈丢失/启动超时能锁止 |
| 风险 | 电流闭环全靠软件，参数不当会导致无力、冲击、超速或误锁 |

### 6.3 `chassis_driver`

| 项 | 内容 |
| --- | --- |
| 目标 | Python ROS2 壳，负责 CAN I/O、Topic、参数加载、里程计发布 |
| 订阅 | `/chassis/intent`, `/cmd_vel`, `/imu/data` |
| 发布 | `/odom`, `/tf`, `/chassis/status` |
| 硬件 | `can0` 独占 |
| 开发任务 | 初始化 SocketCAN；周期查询 ERPM；调用 `chassis_core.tick()`；发送电流帧和心跳；积分里程计；处理 failsafe |
| 验收 | CAN TX/RX 增加；遥控前后转向有效；`/odom` 50Hz；`/chassis/status` 字段正确 |
| 风险 | 不能双开 CAN socket；ERPM 字节序错误会直接污染闭环 |

### 6.4 `remote_driver`

| 项 | 内容 |
| --- | --- |
| 目标 | 解码 SBUS 遥控器并发布 `sensor_msgs/Joy` |
| 输入 | `/dev/ttyS1`，MCU 转发 SBUS；备用 `/dev/ttyS7` |
| 发布 | `/joy` |
| 开发任务 | 25 字节帧同步、16 通道 11-bit 解包、摇杆归一化、开关二值化、失控保护、模拟模式 |
| 验收 | `/joy` 约 71Hz；油门/转向/档位/ESTOP 与实物一致 |
| 风险 | 文档中 CH1/CH3 与参数总表通道存在差异，必须实测锁定 |

### 6.5 `imu_driver`

| 项 | 内容 |
| --- | --- |
| 目标 | 读取 QMI8658 六轴数据并发布 IMU |
| 输入 | `/dev/qmi8658_imu`，24 字节 `<iiiiii` 小端 |
| 发布 | `/imu/data` |
| 开发任务 | 阻塞读线程、缩放 `/1e6`、应用 offset/scale、填充 `sensor_msgs/Imu`，orientation 标记不可用 |
| 验收 | 200Hz 发布；静止时加速度和角速度合理；yaw 积分漂移可监测 |
| 风险 | 协方差待标定，航向 PID 对陀螺零偏敏感 |

### 6.6 `rtk_driver`

| 项 | 内容 |
| --- | --- |
| 目标 | 解析 NMEA 并发布 GNSS 定位 |
| 输入 | `/dev/ttyS2` @ 460800 |
| 发布 | `/fix` |
| 开发任务 | `$GPGGA`/`$GPRMC` 解析、XOR 校验、ddmm.mmmm 转十进制度、质量等级映射协方差、模拟模式 |
| 验收 | `/fix` 1-5Hz；状态 `A` 与 quality 合法；S/W 方向为负 |
| 风险 | 室内/遮挡定位不可用，不能单独承担精确覆盖定位 |

### 6.7 `master_bridge` / `master_controller`

| 项 | 内容 |
| --- | --- |
| 一期目标 | `STANDBY ↔ MANUAL`，遥控到 `/chassis/intent` 桥接 |
| 二期目标 | 扩展为六态状态机：`STANDBY/MANUAL/CRUISING/CLEANING/RETURNING/OBSTACLE_PAUSE` |
| 订阅 | 一期 `/joy`；二期 `/control/cmd/unified`, `/planner/status`, `/fusion/semantic_alert`, 清扫状态 |
| 发布 | `/chassis/intent`, `/cmd_vel`, `/master/state`, `/control/trigger_planning`, `/master/task/mode` |
| 开发任务 | 一期完成遥控映射和急停；二期完成任务调度、低电量/尘满/障碍暂停、清扫闭环 |
| 验收 | 遥控可接管；`AUTO_SWEEP` 可触发规划；障碍告警进入暂停并可恢复 |
| 风险 | 电池/回充接口缺失，`RETURNING` 只能先做占位或人工目标 |

### 6.8 `path_planner`

| 项 | 内容 |
| --- | --- |
| 目标 | 覆盖路径规划、道路清扫、航点执行、局部避障响应 |
| 输入 | `/odom`, `/imu/data`, `/fix`, `/control/trigger_planning`, `/fusion/obstacle/decision` |
| 输出 | `/planner/status`, `/chassis/intent` 或规划状态/路径消息 |
| 开发任务 | 弓字形航点生成、Pure Pursuit/航点执行器、偏差检测、重新规划/等待/减速策略 |
| 验收 | 空旷区域生成航点；按航点行驶；收到 `WAIT/SLOW/DETOUR` 后行为正确 |
| 风险 | 无 LiDAR SLAM 后覆盖精度取决于 odom/IMU/RTK，轮滑会造成漂移 |

### 6.9 `vision_detector`

| 项 | 内容 |
| --- | --- |
| 目标 | BPU YOLO 8 类垃圾/障碍检测，输出检测、清洁度和状态 |
| 输入 | `sensor/camera/image_raw`, 可选深度图/相机内参, `master/task/mode` |
| 输出 | `vision/detect/list`, `vision/detect/cleanliness`, `vision/status`, 可选 `vision/debug/annotated_image` |
| 模型类别 | `recyclable`, `kitchen_waste`, `hazardous`, `other_waste`, `green_waste`, `pedestrian`, `obstacle`, `stain` |
| 开发任务 | 模型加载、预处理、BPU 推理、DetectionArray 填充、清洁度评分、模式感知过滤、模型状态发布 |
| 验收 | 输出时间戳等于原始图像时间戳；检测列表格式正确；清洁度 0=脏 1=净；BPU 推理可持续运行 |
| 风险 | V2 文档中的 TensorRT/ONNX/Jetson 路线不适用，需补齐 ONNX 到 HBM 的平台转换流程 |

### 6.10 `radar_driver`

| 项 | 内容 |
| --- | --- |
| 目标 | 适配毫米波雷达厂商已发布 PointCloud2，生成障碍物/追踪结果 |
| 输入 | `/rys_mmwave/radar_raw_pcl_0..3`, `/rys_mmwave/radar_scan_pcl_0..3`, `/rys_mmwave/points_labeled_0..3` |
| 输出 | `radar/obstacles` 或融合模块约定输入 |
| 开发任务 | 订阅 4 路 PointCloud2、坐标统一、聚类/追踪、输出距离/方位/径向速度 |

## 8. 测试与验收

### 8.1 单元测试

- CAN 帧构造：心跳、电流、查询帧字节序正确。
- CAN 响应解析：ERPM 使用 `DATA[2:6]` big-endian。
- SBUS 解码：25 字节同步、16 通道解包、归一化、失控标志。
- IMU 解析：`<iiiiii` 小端、缩放和校准系数。
- RTK 解析：GGA/RMC 字段、XOR 校验、坐标正负。
- 运动学：ERPM/RPM/线速度转换、里程计积分。
- 状态机：STANDBY、MANUAL、CRUISING、CLEANING、RETURNING、OBSTACLE_PAUSE 转移。
- 视觉接口：DetectionArray 时间戳和字段约束。

### 8.2 台架测试

- `can0` 心跳和查询频率正常。
- 固定小电流作动，确认四轮 ID、方向和电流符号。
- 急停输入后电流立即归零。
- 反馈超时、超速、启动超时进入安全锁。
- `/chassis/status` 电流、轮速、yaw 字段可用于调试。

### 8.3 实车测试

- 遥控前进、后退、左转、右转、原地旋转。
- LOW/MID/HIGH 档位速度变化合理。
- 直行航向保持不发散。
- 换向先停再反转，无明显冲击。
- 低速路径执行能按航点到达。
- 障碍告警能暂停/减速/绕行。
- 清扫策略能启动、停止、反馈状态。

## 9. 冲突、不合理与待确认

### 9.1 文档冲突

1. V2.5 描述 x86/Jetson、LiDAR、ONNX/TensorRT、通用 `motion_controller`；V3 已改为 ARM64 X5、毫米波、BPU `.hbm`、`chassis_driver + chassis_core`。
2. 视觉类别命名在文档间不同：`road_obstacle/pedestrian_pet` 与 V3 的 `obstacle/pedestrian` 需要统一。
3. 参数数值在 V3、参数总表、底盘核心文档之间不完全一致，如 `wheel_radius`、`motor_dirs`、`wheel_max_current`、航向 PID。
4. V2 的 `localization_engine` 基于 LiDAR SLAM，不适用于当前无 LiDAR 平台。
5. `motion_controller/follow_path` 在 V2 是核心模块，但 V3 以 `chassis_driver` 和 `path_planner` 航点执行替代。

### 9.2 实现困难

1. 电机固件只能电流控制，软件要承担速度闭环、启动破静摩擦、堵转、超速和反馈丢失处理。
2. 60kg 实车对电流参数敏感，过低无力，过高有冲击和安全风险。
3. 轮式里程计 + IMU + RTK 替代 SLAM，覆盖路径精度和长期漂移需要实车验证。
4. 毫米波雷达无高度信息，无法单独判定低矮/悬空/可清扫小物体。
5. BPU `.hbm` 部署链路与 V2 训练文档的 TensorRT/ONNX 假设不一致。
6. 视觉检测需要足够本场景数据，公开数据集标签与 8 类目标不完全匹配。

### 9.3 不合理或不可近期交付

1. `cleaning_actuator` 写了刷、吸、洒水、尘满、水箱等能力，但 V3 只明确 CAN ID=005 刀盘，硬件定义不足。
2. 自动回充依赖充电桩定位、电池状态和返航目标，文档没有可实现接口。
3. 电池低电量策略已写入主控，但缺少电池读取来源。
4. App/语音/远程监控属于产品化能力，不应阻塞一期和二期实车闭环。
5. 雷达模块应适配厂商已发布 topic，不应重复做底层驱动。

### 9.4 必须确认

| 项 | 需要确认的问题 |
| --- | --- |
| 参数事实源 | 最终运行的 `phase1_params.yaml` 中 `motor_dirs/wheel_radius/current/PID` |
| 遥控通道 | CH1/CH3/CH4/CH6/CH7 的实际功能映射 |
| 清扫硬件 | 刀盘以外是否存在主刷、边刷、吸力、洒水、尘满传感器 |
| 视觉部署 | ONNX 到 HBM 的工具链、模型输入输出 layout、类别顺序 |
| 毫米波坐标系 | 4 路雷达安装位姿、frame_id、时间戳质量 |
| 电池接口 | 电量、电压、电流、充电状态来源 |
| 回充目标 | 充电站坐标、识别方式、对接控制策略 |

## 10. 近期执行建议

1. 先冻结一期参数和接口，建立 `common + chassis_core + chassis_driver + remote/imu/rtk + master_bridge` 的最小闭环。
2. 用台架和低速实车验证 CAN 电流控制、安全锁、遥控映射和里程计。
3. 再接入 `path_planner` 航点执行，先不做复杂避障。
4. 并行推进视觉 BPU 模型链路和毫米波 topic 适配。
5. 最后做 `fusion_engine + cleaning_actuator`，形成检测、避障、清扫、验证闭环。
