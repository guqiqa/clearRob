## 1. 项目总览

本项目面向智能环卫机器人实车落地，部署于移远 Quectel QSM602HA-GL 开发板，硬件核心为 D-Robotics X5 SoC、ARM64 Ubuntu 22.04、ROS2 Humble、4GB 内存。系统需要同时支持室内和室外运行，采用统一的任务、规划、路径跟踪和安全接口；通过可替换的定位后端适配视觉、RTK 和其他定位来源，通过毫米波雷达与视觉完成障碍感知，通过底盘适配层接入正在调试的新固件。

## 2. 实施原则

1. 当前真实硬件和新固件接口资料优先于旧版本需求文档。
2. 新底盘接口以 `底盘控制接口清单_20260920.md` 为待确认清单；未由固件团队确认的字段不能写死。
3. 上层只使用车体速度和结构化状态，不依赖电机 CAN ID、电流单位和旧固件内部实现。
4. `path_planner` 只输出路径，`motion_controller` 只负责跟踪，`safety_supervisor` 负责最终软件安全仲裁，`chassis_driver` 是唯一硬件出口。
5. 惯性导航和 RTK 是必选基础能力；双目相机、毫米波雷达等均按能力声明和配置启用，不能把选装传感器写成固定依赖。
6. `map -> odom -> base_link` 必须唯一发布和可追踪；定位后端可以替换，但输出契约不变。
7. 传感器切换必须由导航管理器完成，切换前检查时间同步、坐标外参、数据新鲜度和定位质量，切换中禁止多个后端同时发布最终 TF。
8. 室内外都必须有明确的定位降级策略：RTK 不可用不等于系统可以继续高速运行，选装视觉或雷达缺失时也必须按能力降级。
9. 实车安全优先于架构完整性：硬件急停、固件 watchdog、通信超时、反馈失效和软件安全锁必须先于自主能力完成。

## 3. 系统架构

### 3.1 一期底盘链路

```text
SBUS 遥控器
  -> remote_driver
  -> /joy
  -> master_controller
  -> MotionRequest
  -> safety_supervisor
  -> SafeMotionCommand
  -> chassis_driver/chassis_adapter
  -> 新底盘固件

控制板 INS + RTK -> integrated_nav_driver -> /ins/state + /fix -> sensor_manager/localization_engine
双目相机（选装） -> stereo_camera/visual_slam -> /vision/odometry or /vision/pose
毫米波雷达（选装） -> radar_driver -> /radar/obstacles
chassis_driver       -> /chassis/state + /chassis/odom
sensor_manager      -> 可用性/质量/切换状态
localization_engine -> /odom + map/odom/base_link TF
```

一期核心验收是“可控、可停、可观测”：遥控链路稳定，新固件命令和反馈闭环有效，安全出口唯一，里程计/状态可读，急停和超时保护可靠。

### 3.2 二期感知清扫链路

```text
UnifiedCommand/AUTO_SWEEP
  -> master_controller
  -> path_planner
  -> Path / FollowPath.action
  -> motion_controller
  -> MotionRequest
  -> safety_supervisor
  -> SafeMotionCommand
  -> chassis_driver/chassis_adapter
  -> 新底盘固件

sensor_manager      -> 传感器能力与质量状态
localization_engine -> localization/pose
path_planner        -> Path / PlannerState
motion_controller   -> MotionRequest

vision_detector -> vision/detect/list -> fusion_engine
radar_driver    -> radar/obstacles     -> fusion_engine
fusion_engine   -> fusion/semantic_alert -> master_controller
fusion_engine   -> fusion/obstacle/decision -> path_planner
fusion_engine   -> safety/emergency_event -> safety_supervisor
safety_supervisor <- emergency event, obstacle/stop request, localization/fault, manual takeover

master_controller -> cleaning_actuator -> 清扫执行器接口
vision_detector -> vision/detect/cleanliness -> cleaning_actuator/master_controller
```

视觉数据不得直接驱动底盘。所有会影响避障路径的视觉和雷达信息必须经过 `fusion_engine`；所有会导致速度限制或停车的请求必须经过 `safety_supervisor`。

### 3.3 三期产品化链路

```text
App / 远程监控 / 语音
  -> control_gateway
  -> master_controller
  -> 任务、区域、回充和清扫状态机
```

三期只作为架构预留：App、语音、远程监控、自动回充、区域任务管理、多机器人命名空间。当前文档不把它们作为近期实车闭环，除非补齐电池、充电桩、地图、通信协议与安全策略。

### 3.4 定位与坐标路线

```text
必选：惯性导航 + RTK + 底盘里程
                    -> 基础状态估计 -> 唯一 odom -> base_link

定位后端候选：
  A. RTK/INS 全局定位（室外优先）
  B. 双目视觉里程计/SLAM（双目选装且可用时）
  C. 其他后端（按设备能力声明接入）
                    -> 导航管理器选择 -> 唯一 map -> odom
```

- `map -> odom` 只能由当前选定的全局定位后端发布。
- `odom -> base_link` 只能由当前选定的状态估计链路发布。
- 惯性导航和 RTK 永远作为基础状态输入；RTK 质量不足时不能宣称具备全局绝对定位。
- 双目或其他选装后端不可用时，系统可以降级到局部里程/惯性模式，但必须限制速度、任务范围和运行时间。
- 传感器切换必须先完成候选后端预热、质量门控和位姿对齐，再切换最终 TF 发布权；禁止直接跳变。
- `TaskArea`、路径和目标点必须声明坐标系，禁止默认把 `odom` 当作全局地图坐标。

### 3.5 传感器能力与切换路线

新增 `sensor_manager` / `navigation_manager` 作为传感器能力管理和导航后端切换层，负责：

1. 启动时发现已安装传感器、驱动版本、数据话题、坐标系和标定状态。
2. 持续发布每个传感器的 `AVAILABLE`、`DEGRADED`、`STALE`、`FAULT` 状态。
3. 根据室内/室外、任务类型、当前工况和质量指标选择定位与避障组合。
4. 对定位后端执行预热、质量门控、位姿对齐、切换、回退和切换失败处理。
5. 对避障传感器执行独立可用性判断；毫米波和双目可以单独工作，也可以进入融合模式。
6. 记录切换原因、旧后端、新后端、切换时间和切换前后质量指标。

建议支持的配置组合：

| 配置 | 必选输入 | 可选输入 | 适用场景 |
| --- | --- | --- | --- |
| `BASE_ONLY` | INS + RTK + 底盘里程 | 无 | 基础室外/低速验证，RTK质量不足时仅限降级运行 |
| `OUTDOOR_RTK` | INS + RTK + 底盘里程 | 毫米波、双目 | 室外开阔区域，RTK质量良好 |
| `INDOOR_STEREO` | INS + RTK + 底盘里程 | 双目相机 | 室内或遮挡环境，双目定位可用 |
| `RADAR_ASSISTED` | INS + RTK + 底盘里程 | 毫米波雷达 | 视觉不可用时的几何/动态障碍辅助 |
| `STEREO_RADAR_FUSION` | INS + RTK + 底盘里程 | 双目 + 毫米波 | 需要语义、深度和动态障碍互补的场景 |

`BASE_ONLY` 不是无限期的正常导航模式。若 RTK 不满足全局定位质量，且没有可用的选装定位后端，系统必须进入限速、限定区域、暂停或停车策略。

### 3.6 底盘物理与转弯路线

底盘采用 4WD 独立驱动差速滑移结构。当前物理评估基线为：裸机约 60 kg，作业总质量约 75~95 kg，轴距约 0.65 m，轮距约 0.45 m，轮半径约 0.10 m。上述参数来自补充力学评估，必须通过称重、测量和低速实车试验确认后，才能成为运行参数事实源。

由于横向滑移转向阻力较大，尤其是在草地和硬质路面，路径规划默认采用大半径 U 弯、Omega 弯或三点调头，不使用零半径原地自转。运动控制必须满足：

```text
R = |v / w|
|w| <= |v| / R_min
v 接近 0 时，w 必须为 0
```

铲雪、割草、清扫使用不同工况参数包。补充评估中的建议值和一致性校验已收录于 `项目文档/底盘控制接口清单_20260920.md`，其中部分速度、半径和角速度组合存在冲突，运行时取更严格限制，不直接照搬为默认参数。

### 3.7 动作模板与任务调用路线

动作模板用于把高频、可验证的底盘运动组织成带约束的轨迹动作。任务层调用动作意图，`maneuver_manager` 根据空间条件、作业工况、定位质量、底盘能力和安全状态选择具体模板；动作模板不得直接访问 CAN、发布轮速或绕过 `safety_supervisor`。

```text
task_executor / master_controller
            -> 动作意图
            -> maneuver_manager
            -> 模板选择、参数校验、轨迹生成和执行监控
            -> motion_controller
            -> safety_supervisor
            -> chassis_adapter
            -> 新底盘固件
```

定位数据通过统一定位链路提供给动作模板：

```text
integrated_nav_driver + chassis odom + 双目视觉（可选）
            -> localization_engine
            -> 当前位姿、目标误差、定位质量、定位后端状态
            -> maneuver_manager / motion_controller
```

#### 3.7.1 动作模板目录

| 模板/动作意图 | 具体目标 | 推荐场景 | 备注 |
| --- | --- | --- | --- |
| `STRAIGHT_RUN` / `RUN_DISTANCE` | 按目标距离或目标位姿直线行驶 | 覆盖作业、接近目标 | 基础模板 |
| `STOP_AT_POSE` | 到达目标位姿并确认实际停车 | 作业起点、作业点、任务结束 | 必须确认实际速度和底盘停车状态 |
| `ALIGN_HEADING` | 在允许的低速轨迹内对齐车头方向 | 换行前、回接前、任务恢复 | 默认不使用原地旋转 |
| `U_TURN` | 大半径连续换向并进入下一条路径 | 宽阔地头覆盖作业 | 首选高频换行模板 |
| `OMEGA_TURN` | 以 Ω 形轨迹完成平滑换向 | 空间受限或需要降低横向冲击 | 需满足当前 `R_min` |
| `THREE_POINT_TURN` | 前进、倒车、再前进完成换向 | 空间较小且允许倒车 | 启停次数多，须检查倒车安全 |
| `N_SHIFT` / `SHIFT_TO_NEXT_ROW` | 通过组合曲线横向换列，车头最终对齐 | 割草、清扫、覆盖路径换列 | 不是 `linear_y` 纯横移 |
| `REJOIN_PATH` | 从当前位置回接到任务路径 | 避障后、人工接管后、定位恢复后 | 需计算可接入点和曲率约束 |
| `S_BYPASS` / `BYPASS_OBSTACLE` | 绕过局部障碍并准备回接 | 双目/毫米波可用时 | 需由感知模块提供安全走廊 |
| `BACK_OUT` | 沿安全方向低速倒车退出 | 前方受阻、狭窄通道 | 必须有后向安全感知或确认 |
| `POSE_RETURN_REVERSE` | 回到起始位置附近且车头反向 | 特殊调度、测试和指定工艺 | 要求高质量 RTK 或视觉融合，不作为默认掉头 |

动作模板的执行精度分级：

| 定位条件 | 允许能力 |
| --- | --- |
| RTK Fixed 或高质量视觉融合 | 可执行位置闭环、精确停车、回位反向动作，具体阈值以实车标定为准 |
| RTK Float/单点或视觉里程计可用 | 可执行低速 U/Ω 形掉头、N 字换列、路径回接；降低精度要求并持续监测误差 |
| 仅惯导 + 底盘里程 | 仅允许短时、低速、相对运动模板；禁止宣称精确回位，超时或累计误差超限时暂停/停车 |
| 定位质量不足或状态不一致 | 不启动精确动作；等待恢复、切换后端或进入安全停车 |

#### 3.7.3 任务调用与选择规则

任务执行器只调用动作意图，不应依赖某一具体轨迹实现。例如覆盖作业换行时调用 `CHANGE_TO_NEXT_COVERAGE_ROW`，由 `maneuver_manager` 按以下条件选择 `U_TURN`、`OMEGA_TURN`、`THREE_POINT_TURN` 或 `N_SHIFT`：

1. 当前作业模式和载荷参数。
2. 地头可用空间、目标路径间距和障碍物安全走廊。
3. 当前 `R_min`、最大角速度、是否允许倒车和底盘实际反馈。
4. RTK、惯导、底盘里程和双目视觉融合的定位质量。
5. 双目相机和毫米波雷达的存在、标定、数据新鲜度和避障能力。
6. 当前 `safety_supervisor` 状态以及是否已有其他动作占用运动控制权。

同一时刻只能有一个运动动作处于 `RUNNING`。新动作必须等待前一动作完成，或由明确的高优先级中止流程取消前一动作后再执行。动作调用方必须处理成功、定位降级、障碍停车、安全停车、超时和执行失败，不能假设模板一定完成。

典型任务编排：

```text
FollowCoverageRow
    -> CHANGE_TO_NEXT_COVERAGE_ROW
    -> U_TURN / OMEGA_TURN / N_SHIFT
    -> ALIGN_HEADING
    -> FollowCoverageRow

ObstaclePause
    -> BYPASS_OBSTACLE
    -> S_BYPASS
    -> REJOIN_PATH
    -> ResumeMission

ManualTakeoverEnd
    -> RESUME_MISSION
    -> REJOIN_PATH
    -> ALIGN_HEADING
    -> FollowCoverageRow
```

#### 3.7.4 动作执行安全状态机

```text
IDLE
  -> PREPARING
  -> RUNNING
  -> POSITION_CORRECTING
  -> COMPLETED
```

异常状态：

```text
LOCALIZATION_DEGRADED
OBSTACLE_STOP
SAFETY_STOP
TIMEOUT
ABORTED
FAILED
```

执行前必须完成模板存在性、参数范围、坐标系、转弯半径、倒车许可、定位质量、传感器健康、障碍物安全距离、底盘使能和安全状态检查。执行中持续检查定位质量、位姿误差、速度跟踪、轮速/滑移、障碍物距离、底盘故障和命令时效；轻微偏差可降速修正，定位恶化应等待或切换后端，危险障碍和底盘故障必须进入保护停车。

动作完成必须同时满足目标误差阈值、实际线速度/角速度接近零或达到模板要求、底盘状态确认，以及安全状态允许进入下一任务。失败时不得沿用原速度上限，应切换到更保守的降级配置或请求重新规划。

### 3.8 突发事件与行人干扰应急预案（接口预留）

本节先冻结架构边界和接口，不在当前阶段冻结最终距离、时间和速度阈值。详细应急策略应在直接导航和动作模板接近完成、感知延迟和底盘制动能力取得实车数据后推进。任何情况下，突发事件的即时保护不能等待任务层或动作模板完成决策。

#### 3.8.1 两级响应链路

```text
双目/毫米波/定位/底盘/人工输入
              -> EmergencyEvent
              -> safety_supervisor
              -> 限速 / 受控停车 / 保护停车 / 软件急停
              -> SafeMotionCommand

safety_supervisor -> EmergencyState
                   -> master_controller / task_executor
                   -> maneuver_manager / path_planner
                   -> 等待、重新定位、绕行、路径回接、人工确认或任务终止
```

- `safety_supervisor` 负责即时运动安全，任何高风险事件都可以直接触发保护停车。
- `master_controller/task_executor` 负责任务级应急编排，不得覆盖安全层已经锁存的停车状态。
- `maneuver_manager` 只在事件解除、定位质量恢复、传感器状态满足要求并获得恢复许可后，执行 `REJOIN_PATH`、`BACK_OUT` 或其他恢复模板。
- 行人检测结果不能直接变成底盘速度命令；必须经过事件分类和安全仲裁。

#### 3.8.2 事件优先级和预留状态

建议优先级从高到低为：

```text
硬件急停
  > 固件故障/watchdog/通信超时
  > 软件急停
  > 行人或动态障碍进入危险区
  > 静态障碍或绕行走廊失效
  > 定位失效或定位质量不足
  > 动作模板超时/轨迹偏差
  > 普通任务暂停
```

预留应急状态：

| 状态 | 含义 | 默认动作 |
| --- | --- | --- |
| `NORMAL` | 无应急事件 | 按当前任务执行 |
| `CAUTION` | 事件已发现但尚未达到停车条件 | 限速并加强监测 |
| `PROTECTIVE_SLOW` | 风险上升或感知不确定 | 进入更严格速度和转弯约束 |
| `PROTECTIVE_STOP` | 行人/障碍进入保护区，或事件数据不可信 | 受控停车并锁定普通运动请求 |
| `WAITING_CLEAR` | 已停车，等待事件消失和数据连续稳定 | 禁止自动恢复运动 |
| `RECOVERY_CHECK` | 检查定位、传感器、路径和恢复条件 | 只允许恢复检查动作 |
| `MANUAL_REQUIRED` | 需要人工确认、现场检查或复位 | 保持停车并等待人工操作 |
| `MISSION_ABORTED` | 当前任务无法安全恢复 | 停止任务并记录审计信息 |

#### 3.8.3 行人走动干扰预案

行人事件至少分为以下阶段：

```text
发现行人/动态目标
    -> 估计距离、方位、速度、运动趋势和不确定性
    -> CAUTION 或 PROTECTIVE_SLOW
    -> 进入保护区则 PROTECTIVE_STOP
    -> 持续确认目标离开且传感器数据稳定
    -> WAITING_CLEAR
    -> RECOVERY_CHECK
    -> 原动作可安全恢复，或 REJOIN_PATH，或 MANUAL_REQUIRED
```

预留规则如下：

1. 双目和毫米波均可提供事件输入；毫米波可用于距离/动态目标保护，双目可用于行人语义和可通行区域判断，两者冲突时采取更保守结果。
2. 仅有毫米波时，不得宣称完成可靠行人分类，但接近的动态目标仍可以触发减速或保护停车。
3. 双目、毫米波或时间同步失效时，不得继续沿用原有高速配置；按当前 `NavigationSensorProfile.loss_policy` 降速、暂停或停车。
4. 行人短时离开视野不等于事件解除，必须满足连续稳定观测、运动区域重新确认和恢复前安全检查。
5. 动作模板执行中发生行人事件时，立即取消或挂起当前模板；不得继续执行未完成的掉头、倒车或绕障段。
6. 事件解除后，优先从保存的任务上下文计算 `REJOIN_PATH`，不能直接跳回原轨迹的下一个点。
7. 连续重复触发、行人停留、传感器互相矛盾或无法确认安全时，转入 `MANUAL_REQUIRED` 或 `MISSION_ABORTED`。

#### 3.8.4 接口预留

建议在 `cleaning_robot_interfaces` 中预留以下结构化接口：

| 接口 | 方向 | 用途 |
| --- | --- | --- |
| `EmergencyEvent` | 感知/定位/底盘/人工 -> `safety_supervisor` | 统一表达事件类型、来源、等级、位置、速度、置信度、时间戳和建议动作 |
| `EmergencyState` | `safety_supervisor` -> 全系统 | 发布当前应急状态、锁存状态、触发原因、恢复条件和人工复位要求 |
| `RecoveryPlan` | `master_controller/task_executor` -> `maneuver_manager` | 保存原任务、暂停位姿、目标路径、候选恢复模板和恢复限制 |
| `EmergencyAudit` | `safety_supervisor`/任务层 -> 监控/日志 | 记录事件、响应、停车、恢复、人工确认和最终结果 |

预留 Topic 和服务：

```text
/safety/emergency_event       EmergencyEvent
/safety/emergency_state       EmergencyState
/mission/recovery_plan        RecoveryPlan
/safety/acknowledge_emergency  AcknowledgeEmergency.srv
/mission/resume_after_emergency ResumeAfterEmergency.srv
```

`/safety/emergency_event` 只允许产生安全层可处理的事件，不允许携带可绕过安全层的底盘速度。`AcknowledgeEmergency` 和 `ResumeAfterEmergency` 必须校验事件是否解除、传感器是否健康、定位是否满足要求、底盘是否可使能以及是否需要人工复位。

#### 3.8.5 与直接导航和动作模板的关系

```text
直接导航执行中：
  EmergencyEvent -> safety_supervisor 立即限速/停车
  -> 保存导航上下文 -> 事件解除 -> 重新规划或继续路径跟踪

动作模板执行中：
  EmergencyEvent -> safety_supervisor 立即限速/停车
  -> 取消/挂起模板 -> 保存模板进度和起止位姿
  -> 事件解除 -> RECOVERY_CHECK -> 原模板重试或 REJOIN_PATH
```

应急响应不取代直接导航和动作模板，而是作为两者之上的安全和任务恢复层。当前只预留接口、状态和审计字段；详细恢复动作、阈值、行人保护区、清除时间、重试次数和人工确认条件，待基础导航能力接近完成后通过仿真、台架、低速实车和人员安全测试逐步冻结。

## 8. 测试与验收

### 8.1 单元测试

- 新固件协议字段映射、命令序号、时间戳和版本兼容规则正确。
- 旧 CAN 帧构造和 ERPM 解析仅作为兼容测试，不作为新固件验收前提。
- SBUS 解码：25 字节同步、16 通道解包、归一化、失控标志。
- 集成导航适配：惯导/RTK 协议字段、时间戳、坐标方向、协方差和质量状态；具体编码以控制板接口资料为准。
- 运动学：车体速度/轮速换算、里程计积分、最小转弯半径和角速度约束。
- 工况参数：载荷、速度、加速度和转弯半径组合冲突时能报告并取更严格值。
- 状态机：STANDBY、MANUAL、CRUISING、CLEANING、RETURNING、OBSTACLE_PAUSE 转移。
- 动作模板：模板参数校验、坐标系、最小转弯半径、定位质量门控、错误码和动作互斥。
- 应急事件：事件等级、来源、时间戳、置信度、锁存和恢复条件字段完整，不能通过事件接口绕过安全出口。
- 视觉接口：DetectionArray 时间戳和字段约束。

### 8.2 台架测试

- 新固件命令、状态反馈、watchdog 和控制超时行为符合接口清单。
- 急停、保护停车和受控停车可区分，并能记录触发原因。
- 目标速度和实际速度反馈一致性可验证。
- 底盘几何、载荷和制动参数完成测量或实车标定。
- `/chassis/state`、`/chassis/odom` 和安全状态字段可用于调试。
- 动作模板 Action 可发送、取消和超时；`/navigation/maneuver_state` 与底盘实际状态一致。
- 应急接口可发布、锁存、确认和审计；`EmergencyEvent` 能驱动 `safety_supervisor` 进入限速或保护停车。

### 8.3 实车测试

- 遥控前进、后退、非零半径左转和右转。
- 零半径原地自转请求被拒绝或降级为安全停车。
- 铲雪、割草、清扫工况参数在对应场地低速验证。
- 低速、大半径 U 弯或 Omega 弯调头稳定，无明显轮胎撕扯或传动冲击。
- 通过任务意图调用 `U_TURN`、`OMEGA_TURN`、`THREE_POINT_TURN` 和 `N_SHIFT`，模板选择符合空间与工况约束。
- 遇到障碍时能执行 `S_BYPASS -> REJOIN_PATH`；定位降级、动作超时和安全停车均不能继续沿用正常速度上限。
- 人工接管后能通过 `RESUME_MISSION -> REJOIN_PATH` 恢复任务，且同一时刻不存在两个运动模板争抢控制权。
- 模板和直接导航执行中模拟行人进入保护区，均能先保护停车，再按条件等待、人工确认或执行 `REJOIN_PATH`；不能自动穿过未确认安全区域。
- 验证双目、毫米波单独可用、融合可用和传感器失效时的降级策略；行人/动态障碍事件触发优先级符合安全状态机。
- 载荷变化下的加减速、制动距离和实际转弯半径可记录。
- 直行航向保持不发散。
- 换向先停再反转，无明显冲击。
- 路径执行能按满足工况约束的轨迹到达。
- 障碍告警能暂停/减速/绕行。
- 清扫策略能启动、停止、反馈状态。

## 9. 冲突、不合理与待确认

### 9.1 文档冲突

1. V2.5 描述 x86/Jetson、LiDAR、ONNX/TensorRT、通用 `motion_controller`；V3 已改为 ARM64 X5、毫米波、BPU `.hbm`、`chassis_driver + chassis_core`。
2. 视觉类别命名在文档间不同：`road_obstacle/pedestrian_pet` 与 V3 的 `obstacle/pedestrian` 需要统一。
3. 参数数值在 V3、参数总表、底盘核心文档之间不完全一致，如 `wheel_radius`、`motor_dirs`、`wheel_max_current`、航向 PID。
4. V2 的 `localization_engine` 基于 LiDAR SLAM，不适用于当前无 LiDAR 平台。
5. `motion_controller/follow_path` 在旧文档中曾与 `path_planner` 航点执行并行；V2.1 收敛为路径跟踪输出 `MotionRequest`，不直接控制底盘。
6. 补充力学评估给出的速度、最小转弯半径和角速度上限存在组合冲突，不能直接全部作为默认参数。

### 9.2 实现困难

1. 新固件的控制模式、反馈字段、watchdog、制动能力和通信超时尚未冻结。
2. 质量、轴距、轮距、离地间隙和轮胎参数需要称重、测量和实车确认。
3. 差速滑移底盘在硬地和草地上的横向阻力、轮胎损伤和传动冲击需要低速验证。
4. 轮式里程计 + IMU + RTK/视觉定位的覆盖路径精度和长期漂移需要实车验证。
5. 毫米波雷达无高度信息，无法单独判定低矮/悬空/可清扫小物体。
6. BPU `.hbm` 部署链路与旧训练文档的 TensorRT/ONNX 假设不一致。
7. 视觉检测需要足够本场景数据，公开数据集标签与 8 类目标不完全匹配。

### 9.3 不合理或不可近期交付

1. `cleaning_actuator` 写了刷、吸、洒水、尘满、水箱等能力，但 V3 只明确 CAN ID=005 刀盘，硬件定义不足。
2. 自动回充依赖充电桩定位、电池状态和返航目标，文档没有可实现接口。
3. 电池低电量策略已写入主控，但缺少电池读取来源。
4. App/语音/远程监控属于产品化能力，不应阻塞一期和二期实车闭环。
5. 雷达模块应适配厂商已发布 topic，不应重复做底层驱动。

v = 0, w != 0

- 任务层负责恢复、回接或终止；

这一点比很多只写“检测到障碍就停车”的方案完整得多。

- 重启后的默认状态；

结论：P1-02 必须先于大部分一期开发。

文档中多处使用：
- “保护区”；
- “及时停车”；
- “降低速度”；
- “数据稳定”；
- “质量不足”；
- “低速运行”。
但没有给出可执行阈值，例如：
- 最大安全速度；
- 感知数据最大允许延迟；
- 保护区距离；
- 最小停车距离；
- 最大制动减速度；
- 人员清除时间；
- 连续稳定观测帧数；
- 定位质量阈值；
- 速度跟踪误差阈值；

没有这些数据，安全状态机只能停留在概念层。

文档将 INS、RTK、底盘里程定义为基础必选输入，但又要求支持室内运行。室内 RTK 通常不可用，因此必须明确区分：
- 平台必须安装 RTK；
- 运行时必须具备有效全局定位。
当前 BASE_ONLY、INDOOR_STEREO 和“RTK 必选”之间边界还不够清楚。尤其是：

INS    RTK    视觉定位    允许能力
正常    Fixed    无    室外自主
正常    Float    正常    限速自主
正常    无效    正常    室内低速自主

异常    任意    任意    保护停车

但：

- 切换是否允许运动；

这部分必须通过状态机和实车测试冻结，而不能只停留在原则描述。

四、接口和架构完整性问题
1. 接口命名不统一
文档同时出现：
- master_controller
- master_bridge
- control_gateway
- task_executor
- navigation_manager
- sensor_manager
- localization_engine
但没有明确这些名称是：
- 独立节点；
- 进程内组件；
- 逻辑模块；

- /master/state
- /control/trigger_planning
- /planner/status
- /fusion/semantic_alert
文档也承认短期允许 JSON，但安全、任务状态和规划控制接口不宜长期使用字符串。应尽快冻结结构化消息、枚举、时间戳、来源、序号和错误码。

ROS2 系统中尚未明确：
- 传感器 Topic 使用何种 QoS；
- 是否允许可靠传输；
- 是否使用 message_filters；
- 传感器时钟与系统时钟如何同步；
- 时间戳异常如何处理；
- 节点启动顺序；
- lifecycle 状态；
- 节点崩溃自动重启策略；
- 参数热更新是否允许。
对于视觉、毫米波和安全事件，这些不是实现细节，而是系统行为的一部分。

建议由单一硬件总线管理进程统一发送，其他模块通过内部接口提交请求。

五、物理和算法层面的风险
1. 差速滑移里程计不能直接等同于高精度定位
轮胎滑移、载荷变化、地面材质和转弯都会导致里程计误差。文档已经意识到这一点，但目前仍缺少：
- 轮滑估计方法；
- 左右轮速度一致性检测；
- 打滑时里程计协方差如何增大；
- 载荷变化时参数如何切换；
- IMU、RTK、视觉融合的权重策略。
2. 毫米波雷达不能单独承担完整障碍理解
文档正确指出毫米波缺乏高度信息，但仍需把限制写入运行规则：
- 不能单独判定低矮障碍；
- 不能单独区分可清扫垃圾和不可通行障碍；
- 不能单独完成可靠行人分类；
- 多径、地面反射和静态杂波需要专门验证。
3. 视觉 BPU 路线还没有真正打通
必须补齐：
- ONNX 到 HBM 的转换工具链；
- 模型输入尺寸和 layout；
- 量化方式；
- 类别顺序；
- NMS 是否在 BPU 或 CPU 执行；
- 4GB 内存下的峰值占用；
- 相机驱动和推理线程的资源隔离；
- 推理超时后的安全降级。
4. 清扫执行机构定义不足
当前硬件明确的只有刀盘 CAN ID=005，但接口却已经包含：
- 主刷；
- 边刷；
- 吸力；
- 洒水；
- 尘满；
- 水箱；
- 清扫进度。
因此 cleaning_actuator 只能先定义为“刀盘控制子系统”，不能把完整清扫能力作为已具备功能。

六、测试验收仍不够严格
文档列出了大量测试项，但很多是定性描述，例如：
- “稳定出现”；
- “延迟满足低速避障”；
- “无明显冲击”；
- “直行航向保持不发散”；
- “清扫策略可用”。
建议将验收改成可测指标，例如：
- 控制命令端到端延迟 <= X ms；
- 保护停车触发到速度降为零 <= X ms；
- 最大停车距离 <= X m；
- 视觉时间戳延迟 <= X ms；
- 雷达障碍检测召回率 >= X%；
- 行人漏检率 <= X%；
- 轨迹横向误差 <= X cm；
- 航向误差 <= X°；
- 动作取消后不得再发送普通运动指令；
- 安全事件锁存后必须人工确认才能恢复。
当前“按实测冻结”是合理原则，但必须明确冻结时间点、责任人、数据样本和签核方式。

七、文档缺失的系统性内容
以下内容目前基本没有覆盖：
1. 故障树和危险分析：急停失效、误加速、反馈伪造、定位跳变、传感器冲突等故障如何分级。
2. 软件看门狗和进程守护：节点崩溃、死锁、CPU 满载、内存耗尽时的处理。
3. 时间同步方案：PPS、PTP、系统时钟漂移和传感器时间基准。
4. 部署和启动顺序：开机自启、参数校验、设备发现失败时的启动策略。
5. 日志和审计保存策略：事件前后数据窗口、日志大小、掉电保护。
6. 参数版本和回滚机制：phase1_params.yaml 如何签名、校验和回滚。
7. 网络和远程控制安全：鉴权、加密、远程急停权限和断网行为。
8. 地图和任务数据管理：地图来源、版本、坐标系、区域边界和任务持久化。
9. 标定管理：相机内参、雷达外参、IMU 安装方向、标定有效期。
10. 资源预算：CPU、内存、BPU、CAN、磁盘和温度上限。
11. 现场运维流程：升级、维修、传感器更换和重新标定后的验收。
12. 法规和人员安全边界：室外公共区域运行、行人保护、人工确认和责任边界。

八、建议的落地顺序
建议按以下顺序推进：
1. 冻结新底盘控制协议、反馈、watchdog、急停和超时行为。
2. 冻结底盘几何、载荷档位、制动能力、最大速度和最小转弯半径。
3. 单独完成 chassis_driver + safety_supervisor + remote_driver 的实车安全闭环。
4. 补齐 motion_controller 的模块定义、接口和验收。
5. 明确 INS/RTK/视觉定位状态矩阵以及切换期间的停车和限速规则。
6. 冻结所有自定义消息、错误码、QoS、时间戳和节点命名。
7. 完成视觉 BPU 和毫米波数据链路的时间同步、坐标标定和延迟测试。
8. 先验证单传感器降级，再验证融合和应急事件。
9. 最后接入清扫机构、覆盖路径、动作模板和任务恢复。
10. 将 App、语音、自动回充和多机器人功能排除在当前实车闭环之外，待基础系统稳定后再启动。

最终判断：
该文档的架构思路基本正确，安全边界意识较强，具备继续开发的价值；但它还不是可直接执行的完整开发规格书。当前最需要补齐的是新底盘契约、量化安全参数、定位切换规则、motion_controller 定义、ROS2 接口细节、实车测试判据和故障处理闭环。
