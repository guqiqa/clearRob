# 系统结构评估 - 基本任务与可扩展性

> 评估对象：`D:\AIview\cleaning_robot_ws` 当前项目文件。  
> 评估口径：项目仍处于调试阶段，因此高信息量注释、现场测试脚本、临时日志属于调试期可接受现象；本文同时标出稳定联调和上线前需要收敛的部分。  
> 评估边界：本文只评价现有结构、基本任务能力、扩展性和语言/日志精简度，不修改代码。

## 1. 总体结论

当前项目已经形成了较完整的一期 ROS2 底盘控制框架，结构上能够支撑实车调试中的基本任务：遥控器输入、`/chassis/intent` 控制、CAN 电流控制、IMU/RTK 发布、里程计和状态观测。底盘控制核心从 ROS I/O 中分离为 `chassis_core`，有利于保留实车调参成果，也便于后续替换输入来源。

二期自主链路已经具备可扩展骨架：`master_bridge` 已扩展出多状态入口，`path_planner` 能响应 `AUTO_SWEEP/ROAD_SWEEP` 触发并执行简化航点，`fusion_engine` 能作为语义告警网关。但它们还不足以构成完整自主清扫系统：视觉识别、毫米波雷达融合、清扫执行、完整任务生命周期和 Action 接口尚未落地。

语言和日志目前明显偏调试型。这个状态符合当前实车调试阶段的需要，但进入稳定联调或上线前，需要将高频 warn 日志、emoji/中文提示、散落调试脚本和参数重复定义逐步收敛。

## 2. 系统结构评价

### 2.1 现有包与职责

| 模块/包 | 当前职责 | 评价 |
| --- | --- | --- |
| `cleaning_robot_common` | 配置常量、运动学、CAN 协议共享库 | 职责清晰，是当前参数和纯函数复用的基础 |
| `chassis_core` | C++/pybind11 底盘控制核心 | 控制算法与 ROS I/O 分离，结构正确 |
| `chassis_driver` | ROS2 + CAN I/O 壳，订阅控制和 IMU，发布 `/odom`、`/tf`、`/chassis/status` | 一期核心节点，功能覆盖基本底盘任务 |
| `remote_driver` | SBUS 解码并发布 `/joy` | 面向实车调试做了较多硬件适配，价值高 |
| `imu_driver` | QMI8658 原始数据读取并发布 `/imu/data` | 基本满足底盘航向保持和状态观测 |
| `rtk_driver` | NMEA 解析并发布 `/fix` | 能提供 RTK 输入，但当前不是完整定位系统 |
| `master_bridge` | 遥控桥接 + 多模式状态机雏形 | 一期桥接可用，二期调度仍简化 |
| `path_planner` | 弓字形/道路航点生成和 intent 航点执行 | 可调试验证自主行驶，不是完整导航栈 |
| `fusion_engine` | 根据视觉检测类别发布语义告警 | 当前是 semantic alert gateway，不是完整后融合 |
| `cleaning_robot_interfaces` | `Detection`、`DetectionArray`、`UnifiedCommand` | 支撑早期二期骨架，距离完整接口规范仍不足 |
| `cleaning_robot_bringup` | launch 和 YAML 参数 | 支持 `simulate`、`autopilot`，适合分阶段调试 |

### 2.2 结构优点

1. 底盘核心与 ROS I/O 分离，`chassis_core` 负责控制计算，`chassis_driver` 负责 CAN、Topic、TF 和状态发布，边界合理。
2. `cleaning_robot_common` 汇总 CAN 协议、Topic、运动学和部分硬件参数，避免所有节点完全各自硬编码。
3. `phase1_chassis.launch.py` 支持 `simulate` 和 `autopilot`，便于本机无硬件验证、实车一期验证、二期骨架验证分开进行。
4. `/chassis/intent` 作为统一控制入口，适合遥控、App、自主规划等多控制源后续接入。
5. 项目中保留了大量现场调试脚本，对实车方向校准、SBUS 验证、轮速/电流监控很实用。

### 2.3 结构限制

1. 二期接口包未补齐，当前只有少量 msg，缺少路径、融合决策、清扫、状态、Action 等完整接口。
2. JSON Topic 与自定义消息并存，调试期灵活，但长期会带来字段漂移和契约不清。
3. `path_planner` 目前直接用航点执行器输出 `/chassis/intent`，不是带地图、避障和 Action 生命周期的完整规划系统。
4. `fusion_engine` 目前没有毫米波雷达输入和空间关联，只能根据视觉类别发布 `PEDESTRIAN_AHEAD/CLEAR`。
5. 工作区没有 `vision_detector`、`radar_driver`、`cleaning_actuator` 可运行包，完整自主清扫闭环尚未形成。

## 3. 基本任务能力

### 3.1 可完成

| 基本任务 | 当前能力 | 依据 |
| --- | --- | --- |
| 遥控器输入到 ROS | 可完成 | `remote_driver` 解码 SBUS 并发布 `/joy` |
| 遥控桥接到底盘意图 | 可完成 | `master_bridge` 将 `/joy` 转为 `/chassis/intent` 和 `/cmd_vel` |
| CAN 电流控制底盘 | 可完成 | `chassis_driver` 调用 `chassis_core.tick()` 并发送 4 路电流帧 |
| IMU 数据发布 | 可完成 | `imu_driver` 读取 `/dev/qmi8658_imu`，发布 `/imu/data` |
| RTK 数据发布 | 可完成 | `rtk_driver` 解析 NMEA，发布 `/fix` |
| 里程计和 TF 发布 | 可完成 | `chassis_driver` 发布 `/odom` 和 `odom -> base_link` |
| 状态观测 | 可完成 | `/chassis/status` 提供轮速、yaw、estop、电流命令等字段 |

### 3.2 基本可完成，但需实车确认

| 任务 | 需要确认点 |
| --- | --- |
| ESTOP 急停和释放 | `master_bridge` 和 `chassis_driver` 均处理 estop，需要确认释放流程不会残留锁止状态 |
| intent 超时保护 | `/chassis/intent` 超过 `intent_timeout_ms` 后应降级到 `/cmd_vel` 或停机，需实车验证 |
| cmd_vel 超时保护 | `/cmd_vel` 超过 `cmd_vel_timeout_ms` 后应停机，需验证与 intent 优先级交互 |
| 速度反馈超时 | `chassis_core` 依赖反馈有效标志，需确认 CAN 丢帧时能稳定停轮 |
| 安全锁恢复 | 超速、启动超时、丢反馈后如何清锁，需要现场形成操作规程 |
| 航向保持 | IMU 标定、死区、PID 参数已经具备，但直行效果依赖地面和轮胎条件 |

### 3.3 只能用于调试验证

| 任务 | 当前状态 |
| --- | --- |
| `AUTO_SWEEP` 自动覆盖 | `master_bridge` 能触发 `path_planner`，`path_planner` 能生成弓字形航点并执行，但缺少完整任务状态、避障和清扫联动 |
| `ROAD_SWEEP` 道路路径 | 能读取道路 JSON 并反向/正向执行，但依赖 `/root/road_path.json` 和 odom 质量 |
| 语义障碍暂停 | `fusion_engine` 可按视觉类别触发 `PEDESTRIAN_AHEAD`，但当前没有真实视觉/雷达完整输入 |

### 3.4 不能完成

| 任务 | 原因 |
| --- | --- |
| 完整视觉识别 | 工作区没有可运行的 `vision_detector` BPU 推理模块 |
| 毫米波雷达融合 | 工作区没有 `radar_driver`，`fusion_engine` 未实现雷达关联 |
| 清扫执行 | 工作区没有 `cleaning_actuator`，也没有清扫硬件接口实现 |
| 自动回充 | 缺少电池状态、充电桩定位、返航目标和对接控制 |
| 完整任务生命周期 | 缺少 Action、取消、恢复、进度和失败语义的完整实现 |

## 4. 可扩展性评价

### 4.1 扩展方向正确

当前架构已经具备继续扩展的基本形状：

1. 硬件驱动节点相对独立，后续增加雷达、视觉、清扫节点不会直接改底盘核心。
2. `/chassis/intent` 把底盘控制抽象成油门、转向、档位、刀盘、急停，便于多来源控制。
3. launch 中 `autopilot` 开关允许二期节点逐步接入，降低调试风险。
4. 参数集中到 YAML，实车调参可以不重编译 C++。
5. `chassis_core` 通过 pybind11 暴露同步接口，后续可以继续增强控制核心而不改变 ROS 外壳大结构。

### 4.2 扩展风险

1. 接口规范尚未稳定：JSON 字符串、少量自定义 msg、未来 Action 三种形态并存。
2. `cleaning_robot_interfaces` 当前过小，二期一旦推进会快速遇到消息缺口。
3. 参数事实源仍有分散：`phase1_params.yaml`、`config.py`、节点内默认参数都存在默认值。
4. 二期状态机和任务执行还偏脚本式，缺少可取消、可恢复、可查询的任务生命周期。
5. 调试脚本散落在 `src` 根目录，短期方便，长期会干扰包边界和工程可读性。

### 4.3 推荐扩展路径

| 阶段 | 建议 |
| --- | --- |
| 当前调试期 | 保持现有节点形态，优先验证底盘安全、遥控、里程计和航点执行 |
| 稳定联调前 | 补齐接口包，统一参数事实源，给高频日志加开关，梳理急停/恢复语义 |
| 二期开发期 | 增加 `vision_detector`、`radar_driver`、`cleaning_actuator`，将 `fusion_engine` 从语义告警升级为后融合 |
| 上线前 | 将任务改为 Action/状态机生命周期，建立测试目录和日志规范 |

## 5. 语言与日志精简度评价

### 5.1 调试期可接受

1. 中文注释和详细背景说明较多，有利于现场调试和团队交接。
2. `remote_driver`、`chassis_driver`、`phase1_params.yaml` 中保留了大量实车调参原因，这对当前阶段很有价值。
3. 调试脚本大量使用 `print()`，作为现场工具可以接受。
4. `master_bridge`、`path_planner`、`fusion_engine` 的中文日志和 emoji 对人工观察很直观，适合早期调试。

### 5.2 稳定联调前需收敛

1. `chassis_node.py` 的 `_tick_ctrl()` 中存在每 50ms 的 `DBG3/DBG2/DBG` warn 日志。调试期可以保留，但应加参数开关或降级为 debug，否则会淹没真正的安全告警。
2. 生产节点中的中文 + emoji 日志建议逐步改为短句、稳定关键字、可 grep 的格式。
3. 错误、告警、状态切换、周期采样应区分日志级别，避免所有现场信息都走 warn。
4. 测试脚本建议后续移动到 `tools/` 或 `scripts/`，避免与 ROS 包源码混在一起。

### 5.3 上线前需处理

| 项 | 建议 |
| --- | --- |
| 高频调试日志 | 默认关闭，通过参数或环境变量开启 |
| 关键事件日志 | 保留启动、急停、故障、安全锁、状态切换 |
| 周期状态 | 用 `/chassis/status`、监控工具或 debug 日志承载，不走 warn |
| 文案语言 | 生产日志尽量统一中英文和关键字格式 |
| 调试工具 | 独立目录管理，标明是否可在实车运行时使用 |

## 6. 明确问题清单

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| `chassis_driver` 状态数组预留电流反馈，但 CAN read loop 主要解析 ERPM | `/chassis/status[11-14]` 可能长期为 0 或无真实含义 | 后续若需要电流反馈，应发送 `CAN_QUERY_CURRENT` 并解析 |
| `phase1_params.yaml` 与 `config.py` 默认值存在差异 | 维护时容易误读实际生效参数 | 明确 YAML 为实车事实源，`config.py` 只作为默认值 |
| 遥控通道描述在不同位置存在命名差异 | 新人容易误判 SWA/SWB/gear/estop | 以当前实测 YAML 和 `remote_node.py` 为准，另写通道冻结表 |
| `fusion_engine` 只是 semantic alert gateway | 不能代表完整后融合能力 | 二期需加入雷达输入、空间关联和决策消息 |
| 缺少 `vision_detector`、`radar_driver`、`cleaning_actuator` 可运行包 | 不能完成完整自主清扫 | 二期按模块补齐 |
| `cleaning_robot_interfaces` 消息不足 | 二期扩展会缺少契约 | 补齐 TaskMode、FusionDecision、CleanStrategy、状态/Action 等 |
| 现有测试多为现场脚本 | 不利于 CI 和回归 | 增加最小单元测试和接口测试目录 |

## 7. 分级整改建议

### 7.1 调试期继续保留

- 详细注释和参数调试记录。
- 现场验证脚本，如 SBUS、方向校准、轮速/电流监控。
- 关键路径日志，尤其是急停、CAN 打开失败、IMU 标定、安全锁。
- `simulate` 和 `autopilot` 开关。

### 7.2 稳定联调前处理

- 给 `chassis_node.py` 高频 `DBG` warn 日志增加参数开关或改为 debug。
- 明确 `_stop()` 发布 `estop=1` 的语义：区分“普通停车”和“急停锁止”。
- 冻结遥控通道映射表，避免 CH5/CH6/CH7 命名漂移。
- 明确 `phase1_params.yaml` 是实车参数事实源。
- 扩展 `cleaning_robot_interfaces`，至少满足二期规划、融合、清扫状态。

### 7.3 上线前处理

- 统一日志风格和日志级别。
- 将调试脚本移入 `tools/` 或 `scripts/`。
- 增加单元测试、launch smoke test、接口契约测试。
- 将二期任务执行改为 Action 或明确的状态机生命周期。
- 补齐 `vision_detector`、`radar_driver`、`cleaning_actuator`。

## 8. 最终评价

现有系统结构能够支撑一期底盘基本任务，适合作为实车调试和参数迭代的平台。底盘链路的核心设计是正确的：控制核心独立、ROS I/O 清楚、参数可配置、遥控到 CAN 的链路完整。

可扩展性方向也是正确的，但二期目前还是骨架：`path_planner` 可做航点调试，`fusion_engine` 可做语义暂停调试，尚未形成真实感知、融合、清扫闭环。

语言和日志目前服务于调试，不需要立即按生产标准清理；但必须在稳定联调前收敛高频 warn 日志、参数事实源、接口契约和任务生命周期。整体判断：**一期可继续实车调试，二期可在当前架构上扩展，但不能把当前状态视为完整自主清扫系统。**
