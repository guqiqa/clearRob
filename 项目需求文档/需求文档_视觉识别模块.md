## 1. 模块定位

视觉识别模块（`vision_detector`）是智能环卫机器人感知系统的核心组件，承担**垃圾检测与分类、障碍物识别、可通行区域判断、清洁度评估**四项职能。

模块属于"使用平台"，与训练平台、验证平台形成**闭环**：

```
训练平台 ──(模型文件)──→ 验证平台 ──(评估确认)──→ 使用平台(视觉模块)
    ↑                                                    │
    └────────────── (反馈数据/增量标注) ──────────────────┘
```

三个平台之间仅通过**模型文件 + 配置文件**传递信息，无运行时依赖。

## 2. 功能需求

### 2.1 垃圾检测与分类

| 项目 | 内容 |
|------|------|
| 任务类型 | 目标检测（Object Detection） |
| 模型 | YOLO 系列（YOLOv8 → YOLOv10），支持版本切换 |
| 输入 | RGB 图像（Camera 采集），原始分辨率 ≥ 1280×720 |
| 预处理 | 保持宽高比 resize 到模型输入尺寸 640×640（letterbox padding 灰色填充），像素归一化到 [0, 1] |
| 输出 | 检测列表：每个目标包含类别、置信度、边界框（xyxy 像素坐标）、像素面积 |

**检测类别体系（8 类，含清扫/避障逻辑）：**

| 类别 | 定位 | 具体目标 | 应对策略 |
|------|------|----------|----------|
| `recyclable` | 可回收垃圾 | 塑料瓶、易拉罐、纸盒、玻璃瓶、金属罐、**大型纸箱** | 减速 → 扫入收集仓 |
| `kitchen_waste` | 厨余垃圾 | 果皮、菜叶、食物残渣 | 先吸 → 后拖 |
| `hazardous` | 有害垃圾 | 电池、药品包装 | 单独收集 + 告警上报 |
| `other_waste` | 其他垃圾 | 塑料袋、烟头、纸屑、一次性餐具 | 直接吸扫 |
| `green_waste` | 绿化垃圾 | 落叶、枯枝 | 直接吸扫 |
| `road_obstacle` | **道路障碍物**（非垃圾） | 石块、砖块、锥桶、路障、垃圾桶、花盆、树木、车辆（轿车/摩托车/电动车）、门 | **绕行避让，不清扫** |
| `pedestrian_pet` | 行人/宠物 | 行人、骑行者、街边摊贩、狗、猫 | **减速/绕行/等待** |
| `stain` | 污渍/水渍 | 地面污渍、积水 | 污渍：判定是否需洒水重拖；**积水：判断面积大小，大面积积水绕行，小面积按污渍处理** |


### 2.2 障碍物识别（与融合模块协同）

**道路障碍物（road_obstacle）：** 视觉识别出非垃圾类障碍物后发布至 `vision/detect/list`。融合模块（`fusion_engine`）将 2D 检测框与 LiDAR 3D 点云空间关联后判定避障：

```
LiDAR 3D 点云 + 视觉 2D 检测框
         ↓
    fusion_engine 空间关联
         ↓
  判定是否需绕行 → fusion/obstacle/decision → path_planner 执行绕行 / 等待
```

| 融合判定 | 视觉判定 | 行为 |
|-----------|----------|------|
| 需绕行 | road_obstacle / pedestrian_pet | 绕行避让 + 上报位置 |
| 需绕行 | 其他垃圾类别 | 先清扫再通过（小物件碾压/大物件先吸扫） |
| 可通行 | 任意类别 | 不触发绕行，按清扫策略执行 |

**行人/宠物（pedestrian_pet）：** 检测行人、骑行者、宠物等动态目标。由融合模块标记为动态障碍，路径规划模块执行减速等待而非清扫。

**积水/污渍（stain）：** 对于城市环卫场景，积水需要判断面积大小：
- **小面积积水**：不影响通行，按污渍流程处理（洒水+重拖）
- **大面积积水**：融合模块判定为通行障碍，触发绕行。面积阈值由 LiDAR 提供的三维尺寸判断

### 2.3 可通行区域判断

- **推断方法**：基于检测框的下半部自由空间推断。将图像下半部分（地面区域）中未被障碍物检测框（`road_obstacle`、`pedestrian_pet`）覆盖的区域标记为可通行，不做语义分割以避免模型复杂度增加
- 输出 `vision/detect/drivable` Topic：`sensor_msgs/msg/Image` 格式的二值掩膜（MONO8 编码，0=不可通行，255=可通行），与输入图像等比例缩放至 640×320
- 发布频率与推理帧率同步
- **调试/辅助 Topic，不接入 path_planner 的订阅链路。** 避障决策由 fusion_engine 经由 `fusion/obstacle/decision` 统一下发，drivable 仅用于调试可视化和方案验证

### 2.4 清洁度评估

- 推理时对当前视野区域输出清洁度评分：**0.0 = 极脏（画面内充满垃圾），1.0 = 完全洁净（无垃圾检测）**
- 计算公式：
  ```
  garbage_area_ratio = Σ(每个检测框的像素面积) / (图像总像素面积)
  cleanliness = max(0.0, 1.0 - garbage_area_ratio / CLEANLINESS_SATURATION_RATIO)
  ```
  其中 `CLEANLINESS_SATURATION_RATIO = 0.3`（当垃圾面积占比 ≥ 30% 时清洁度饱和为 0.0）
- 仅统计垃圾类别（class_id 0~4）的面积；道路障碍物、行人/宠物和污渍不参与清洁度计算
- 输出 `vision/detect/cleanliness` Topic：`std_msgs/msg/Float32`，固定频率 1Hz
- 清扫模块订阅后判断是否需要重扫：当 cleanliness < 0.7 且连续 3 次评估均低于阈值时，判定为重扫

### 2.5 模式感知检测策略

订阅 `master/task/mode`，根据主控调度下发的运行模式调整检测策略：

| 模式 | 检测范围 | 检测频率 | drivable 输出 | 行为说明 |
|------|----------|----------|---------------|----------|
| `CRUISE` | 全类别（8 类） | 全帧率 | 是 | 正常巡航，全量检测；发现垃圾时由 master_controller 决定是否转入 CLEAN |
| `CLEAN` | class_id 0~4（垃圾）+ 7（污渍） | 全帧率 | 否（路径已规划） | 侧重检测清洁效果；每帧输出 cleanliness 供清扫模块判断重扫 |
| `RETURN` | class_id 5~6（road_obstacle + pedestrian_pet） | 全帧率 | 否 | 返航途中仅检测障碍物确保通行安全，关闭垃圾检测以节省算力 |

- mode 切换到 CLEAN 时，提高 cleanliness 发布频率至与推理帧率同步（临时覆盖 `cleanliness_interval_s`）
- mode 离开 CLEAN 时，恢复 cleanliness 默认 1Hz 频率
- mode 切换延迟 ≤ 1 帧（下一帧即采用新模式策略）

## 3. ROS2 接口规范

### 3.1 Node 信息

| 项目 | 内容 |
|------|------|
| ROS2 Node | `vision_detector` |
| 语言 | Python 3.10+（推理主逻辑）+ C++（图像预处理，性能敏感部分） |
| 生命周期 | ROS2 Managed Lifecycle（Unconfigured → Inactive → Active） |

### 3.2 订阅

| Topic | 消息类型 | QoS | 说明 |
|-------|---------|-----|------|
| `sensor/camera/image_raw` | `sensor_msgs/msg/Image` | Sensor Data, KeepLast(5) | RGB 图像输入 |
| `master/task/mode` | `cleaning_robot_interfaces/msg/TaskMode` | Sensor Data, KeepLast(1) | 模式切换（CRUISE/CLEAN/RETURN），触发检测策略调整 |

### 3.3 发布

| Topic | 消息类型 | 频率 | 说明 |
|-------|---------|------|------|
| `vision/detect/list` | `cleaning_robot_interfaces/msg/DetectionArray` | 与推理帧率同步 | 检测列表 |
| `vision/detect/cleanliness` | `std_msgs/msg/Float32` | 1Hz（CLEAN 模式升至推理帧率） | 清洁度评分，0.0=极脏，1.0=洁净 |
| `vision/detect/drivable` | `sensor_msgs/msg/Image` | 与推理帧率同步 | 调试/辅助 Topic，不接入 path_planner 的订阅链路。避障决策由 fusion_engine 经由 fusion/obstacle/decision 下发 |
| `vision/status` | `cleaning_robot_interfaces/msg/VisionStatus` | 1Hz | 模块运行状态 |
| `vision/debug/annotated_image` | `sensor_msgs/msg/Image` | 条件发布 | 标注后的图像（仅 `publish_annotated_image=true` 时发布） |
| `system/heartbeat/vision_detector` | `cleaning_robot_interfaces/msg/Heartbeat` | 1Hz | 心跳 |

### 3.4 Service

| Service | 类型 | 说明 |
|---------|------|------|
| `vision/set_model` | `cleaning_robot_interfaces/srv/SetModel` | 运行时热切换模型（参数：模型文件路径） |
| `vision/get_status` | `cleaning_robot_interfaces/srv/GetStatus` | 查询当前状态（活跃模型名、平均帧率、延迟、状态码） |

### 3.5 自定义消息定义

```text
# Detection.msg — 单个检测目标
# 坐标系统：xmin,ymin,xmax,ymax 为像素坐标（相对于原始相机图像分辨率，左上角为原点）
# 坐标由 vision_detector 直接从 YOLO 推理输出取整后填入，fusion_engine 负责结合相机内参完成 2D→3D 投影
string   class_name          # 类别名称（与8类检测体系一致）
float32  confidence          # 置信度 (0.0~1.0)
uint16   class_id            # 类别 ID (0~7，见类别体系表)
int32    xmin                # 边界框左上角 x 像素坐标（0-indexed）
int32    ymin                # 边界框左上角 y 像素坐标（0-indexed）
int32    xmax                # 边界框右下角 x 像素坐标（exclusive）
int32    ymax                # 边界框右下角 y 像素坐标（exclusive）

# DetectionArray.msg — 一帧检测结果（vision_detector 发布至 vision/detect/list）
# ⚠️ 关键契约：Header.stamp 必须设置为摄像头原始图像的时间戳
#   （即 sensor_msgs/Image.header.stamp），严禁使用节点发布时的系统当前时间。
#   时间戳偏差会导致 fusion_engine 在做 2D 检测框与 LiDAR 点云空间关联时出现坐标漂移。
std_msgs/Header  header      # stamp = 相机图像时间戳；frame_id = camera 光心坐标系
Detection[]      detections  # 当前帧所有检测目标（可为空数组）
uint32           frame_seq   # 帧序号（单调递增，溢出归零）— 调试用
float32          inference_ms # 本次推理耗时 (ms) — 调试用

# VisionStatus.msg — 运行状态（粒度细于 Heartbeat）
# Heartbeat.error_code 仅表示心跳层面错误（0=正常，非0=进程级异常）
# VisionStatus.status 表示业务级运行状态，两者独立
string   active_model        # 当前加载的模型文件名
float32  avg_inference_ms    # 最近 30 帧平均推理耗时
float32  fps                 # 实际帧率
uint8    status              # 0=正常 1=降级（帧率受限但可用） 2=故障（无输出）
string   status_text         # 状态描述（status=1时说明降级原因，status=2时说明故障原因）

# SetModel.srv
string   model_path          # 请求：模型文件路径（.pt / .onnx / .engine）
---
bool     success             # 响应：是否加载成功
string   message             # 响应：成功时返回模型摘要，失败时返回错误原因

# Heartbeat.msg — 心跳（1Hz，所有模块统一格式）
std_msgs/Header  header
string   node_name           # "vision_detector"
uint8    lifecycle_state     # 1=Unconfigured, 2=Inactive, 3=Active, 4=Finalized
uint8    error_code          # 0=进程正常 1=初始化失败 2=运行时异常退出
```

### 3.6 ROS2 Parameters（YAML 配置）

```yaml
vision_detector:
  ros__parameters:
    # 模型
    model_path: "/path/to/models/cleaning_v1.0.0_s_best.engine"  # 模型文件路径（.pt / .onnx / .engine）
    model_config: "/path/to/models/cleaning_v1.0.0_s_config.yaml" # 模型元信息（类别定义、输入规格）
    model_version: "yolov8"                # yolov8 / yolov9 / yolov10
    conf_threshold: 0.45                   # 置信度阈值（低于此值的检测框丢弃）
    nms_iou_threshold: 0.45                # NMS IoU 阈值
    input_width: 640                       # 模型输入宽度
    input_height: 640                      # 模型输入高度
    
    # 推理
    device: "cuda:0"                       # cuda:0 / cpu / tensorrt
    half_precision: true                   # FP16 推理
    max_batch_size: 1                      # 最大批次（端侧固定为 1）
    
    # 后处理
    enable_tracking: false                 # 是否启 bytetrack 多目标追踪
    publish_annotated_image: false         # 是否发布标注后图像至 vision/debug/annotated_image
    
    # 性能
    target_fps: 30.0                       # 目标帧率
    warn_latency_ms: 50.0                  # 延迟告警阈值 (ms)
    degrade_fps_ratio: 0.5                 # 降级时帧率降低比例（降为目标帧率的 50%）
    
    # 清洁度
    cleanliness_interval_s: 1.0            # 清洁度评估周期间隔（CLEAN 模式下自动升至推理帧率）
    cleanliness_saturation_ratio: 0.3      # 清洁度饱和阈值（垃圾面积占比超过此值，cleanliness=0.0）
```

## 4. 性能指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 推理帧率 | ≥ 30 FPS（GPU）, ≥ 15 FPS（Jetson Orin） | 环卫低速场景，15FPS 即可满足 |
| 推理延迟 | ≤ 33ms (GPU) / ≤ 66ms (Jetson Orin) | 单帧端到端（不含通信） |
| mAP@0.5 | ≥ 0.85 | 垃圾检测任务，IoU=0.5 |
| mAP@0.5:0.95 | ≥ 0.65 | 更严格的评估 |
| 召回率 (Recall) | ≥ 0.90 | 重点保证不漏检，可接受一定误检 |
| 模型大小 | ≤ 50MB (ONNX/TensorRT) | 便于端侧部署 |
| 启动加载时间 | ≤ 5s | 从加载模型到首帧推理 |
| 模型热切换时间 | ≤ 3s | Service 触发到新模型就绪 |

## 5. 训练平台

训练平台为独立子系统，在本机（本地工作站 / GPU 服务器）运行，负责从标注数据中训练出符合部署标准的 YOLOv8 模型。

### 5.1 平台定位与环境

| 项目 | 内容 |
|------|------|
| 定位 | 模型生产线——输入标注数据，输出标准模型文件 |
| 运行位置 | 本机（训练工作站），非边缘端 |
| 框架 | PyTorch 2.x + Ultralytics YOLOv8 |
| Python | 3.10+ |
| GPU 要求 | NVIDIA GPU ≥8GB 显存（推荐 RTX 3060+ / A4000+），CUDA 11.8+ |

### 5.4 训练流程


### 5.5 训练产出检查

每轮训练完成后自动执行以下检查，不通过则训练标记为失败：

|--------|------|------|

| 过拟合检测 | val loss 与 train loss 差值 < 0.5 | 防止严重过拟合 |

## 8. 模块间交互关系（vision_detector 视角）

```
┌──────────────────┐
│ sensor/camera    │── image_raw (订阅) ──→ ┌─────────────────────────┐
└──────────────────┘                       │    vision_detector       │
                                           │                          │
┌──────────────────┐                       │  发布 ──→ ──→ ──→ ──→ ──┤
│ master_controller│── task/mode (订阅) ──→│  detect/list    → master_controller    │
└──────────────────┘                       │                 → cleaning_actuator    │
                                           │                 → fusion_engine       │
                                           │  cleanliness   → master_controller    │
                                           │                 → cleaning_actuator    │
                                           │  drivable      → (调试/辅助，不接入   │
                                           │                   path_planner)        │
                                           │  status        → master_controller    │
                                           │  heartbeat     → master_controller    │
                                           └─────────────────────────┘
```

**后融合协作（vision_detector → fusion_engine）：**

```
vision_detector ── detect/list ──→ fusion_engine
                                      │
                                      │ 接收 2D 检测框
                                      │ + LiDAR 3D 点云
                                      │ 空间关联 → 3D 目标位置+尺寸+类别
                                      │
                                      ├── fusion/3d_target → master_controller (告警)
                                      └── fusion/obstacle/decision → path_planner (避障)
```

视觉模块只做 2D 检测，不依赖 LiDAR。融合模块（`fusion_engine`）独立完成视觉+LiDAR 后融合。视觉出故障时融合模块降级为纯 LiDAR 模式，不影响独立避障。

**物理隔离原则：vision_detector 不直接向 path_planner 发布任何 Topic。** 视觉检测结果（`vision/detect/list`）的唯一消费者为 master_controller、cleaning_actuator 和 fusion_engine。`vision/detect/drivable` 为调试/辅助 Topic，不接入 path_planner 的订阅链路。所有影响导航的视觉信息均通过 fusion_engine 2D→3D 空间关联后，以 `fusion/obstacle/decision` 的形式统一下发至 path_planner。

## 9. 数据与标注

### 9.1 数据来源

| 来源 | 类型 | 原始标注格式 | 说明 |
|------|------|-------------|------|
| TACO | 公开集 | COCO JSON | 室内外垃圾数据集，原始 60 类 |
| UAVVaste | 公开集 | COCO JSON | 无人机视角垃圾，原始 4 大类 |
| TrashNet | 公开集 | 按类别分文件夹 | 单一物体分类， 6 类（纸质、玻璃、金属、塑料等） |
| 自采集 | 自建 | YOLO txt | 环卫作业场景，按需补充 |

> 公开数据集的标签体系与项目所需 8 类标签**不一致**，需通过代码统一转换为项目标签后再参与训练。

### 9.2 标签映射方案

**映射总表（公开集原始标签 → 项目标准标签）：**

| 项目标签 (target) | TACO 原始标签 | UAVVaste 原始标签 | TrashNet 原始标签 |
|-------------------|-------------|-------------------|-------------------|
| `recyclable` (0) | Metal, Plastic, Glass, Aluminium foil, Aerosol, Paper, Cardboard, Corrugated carton, Polypropylene, Other carton, Tetrapak, Scrap metal, Aluminium blister | metal, plastic, glass, paper, cardboard | glass, metal, plastic, paper |
| `kitchen_waste` (1) | Food waste, Organic, Leftover food, Coffee grounds, Tea bags, Fruit peel, Bone | food_waste, kitchen | — |
| `hazardous` (2) | Battery, E-waste, Medicine, Fluorescent tube, WEEE, Light bulb | battery, e_waste, chemical | — |
| `other_waste` (3) | Cigarette, Disposible cup, Disposible cutlery, Styrofoam, Foam, Rope, Straw, Unlabeled litter, Toilet paper tube, Tissue paper | — | trash, cardboard (部分) |
| `green_waste` (4) | Leaf, Wood, Branch, Grass | — | — |
| `road_obstacle` (5) | Furniture, Tire, Large object, Construction debris | — | — |
| `pedestrian_pet` (6) | — | — | — |
| `stain` (7) | — | — | — |

> `pedestrian_pet` 和 `stain` 在现有公开数据集中无对应标签，由自采集数据补充。`pedestrian_pet` 可额外引入公开行人/车辆数据集扩增。

**映射规则：**

1. 不在上表中的原始标签 → **丢弃**（非环卫场景关注类别）
2. 同一原始标签仅映射到**一个**目标类别，不一对多
3. TrashNet 按文件夹名判类，需额外处理分类数据 → 检测格式转换（整图标注框）
4. 映射后每类样本量不满足 ≥500 框时 → 数据增强补充或自采集补齐

### 9.3 标注格式转换

| 源格式 | 目标格式 | 转换内容 |
|--------|----------|----------|
| COCO JSON（TACO, UAVVaste） | YOLO txt | category_id 映射 + bbox [x,y,w,h] → [x_center,y_center,w,h] 归一化 |
| 文件夹分类（TrashNet） | YOLO txt | 按文件夹名判类 → 整张图作为检出目标生成标注（x_center=0.5, y_center=0.5, w=1.0, h=1.0） |
| 自采集 | 直接按 YOLO txt 标注 | 无需转换 |

## 10. 容错与降级

| 故障场景 | 检测方式 | 响应行为 |
|----------|----------|----------|
| Camera 断连/故障 | `sensor/camera/image_raw` 超时（>2s 无帧） | 发布 status=2（故障），cleanliness=-1.0，停止发布 detect/list；等待主控调度决定 |
| 推理耗时持续超标 | avg_inference_ms > warn_latency_ms 持续 30s | 发布 status=1（降级），帧率降至 target_fps × degrade_fps_ratio（默认 15FPS），写入 status_text="latency_warn: {avg_ms}ms" |
| GPU 显存不足 | CUDA OOM 捕获 | 尝试切换至 CPU 推理或 TensorRT INT8；CPU 切换成功 → status=1(status_text="gpu_oom: switched to CPU")；失败 → status=2(status_text="gpu_oom: fallback failed") |
| 模型文件无效或损坏 | set_model 或启动加载时校验失败（文件不存在/格式不匹配/checksum 错误） | 发布 status=2（status_text="model_load_failed: {reason}"），当前无模型时不发布 detect/list，等待新的 set_model 调用恢复 |
| 模型热切换（set_model） | Service 调用触发 | 切换期间继续用当前模型输出 detect/list（无缝切换）；新模型加载成功后瞬间切换（第一帧即用新模型）；加载失败则保留旧模型运行，status 不变，Service 返回 success=false |
| 连续无检测 | 连续 10s 无任何检测结果但图像正常流入 | 正常场景（干净区域），cleanliness=1.0，不触发降级 |

**降级模式（status=1）行为汇总：**
- detect/list：仍正常发布（延迟升高但功能可用）
- cleanliness：仍正常发布
- drivable：仍正常发布
- 帧率：降至 target_fps × degrade_fps_ratio
- 由 master_controller 综合判断是否继续清扫、暂停或返航

**故障模式（status=2）行为汇总：**
- detect/list：停止发布
- cleanliness：发布 -1.0（表示无数据）
- drivable：停止发布
- vision/status：持续发布，status_text 记录故障原因
- 不接受除 set_model 外的 Service 调用
- 等待外部恢复（主控调度降级、Camera 恢复后自动重连）

### 11.2 模式切换时序

```
master_controller          vision_detector
     │                         │
     │ master/task/mode        │
     │ (CLEAN)                 │
     │────────────────────────→│
     │                         │ 下一帧起: 仅检测垃圾+污渍
     │                         │ cleanliness 升至推理帧率
     │                         │ drivable 停止发布
     │                         │
     │                         │ (清扫完成...)
     │ master/task/mode        │
     │ (CRUISE)                │
     │────────────────────────→│
     │                         │ 下一帧起: 恢复全类别检测
     │                         │ cleanliness 恢复 1Hz
     │                         │ drivable 恢复发布
```

### 11.3 降级恢复序列

```
vision_detector          master_controller
     │                         │
     │ (30s 内 avg_latency>50ms)│
     │                         │
     │ vision/status           │
     │ (status=1,              │
     │  latency_warn)          │
     │────────────────────────→│
     │ (帧率自降至 15FPS)      │ 综合判断
     │                         │─────
     │                         │ 若在执行 CLEAN → 维持清扫
     │                         │ 若在 CRUISE → 继续巡逻

     │                         │
     │ (延迟恢复<50ms)          │
     │ vision/status           │
     │ (status=0)              │
     │────────────────────────→│
     │ (帧率恢复至 target_fps) │ 恢复正常调度
```
